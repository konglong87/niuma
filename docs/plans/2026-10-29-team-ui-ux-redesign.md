# Team 编排工作台 UI/UX 重设计（2026-10-29）

## 决策与边界

本次仅改桌面 V2 Team 编排工作台的呈现和交互，不改工作流/Agent API、模型设置、运行语义、单 Agent、Computer Use 或 screen profile。Team 是在现有 profile/模型路由之上的编排入口，不另造一套身份或运行配置。目标是普通用户在 1024×700 的真实窗口里能看懂「选模板/建 Agent → 配步骤 → 输入目标 → 跟踪结果」，无需理解 DAG、epoch 或内部 ID。

不采用大面积渐变、彩色框、随机卡片、流程画布或模糊玻璃效果。沿用 `web/src/v2/styles.css` 的现有明暗主题 token；中性色承载布局，蓝色仅强调主要操作和焦点，成功/警告/失败只表达状态。与桌面宠物、侧栏视觉保持同一产品。

## 基于代码和真实截图的审计

- `WebUIV2App.tsx` 只在 V2 workflows route 挂载 `WorkflowWorkbench`，`routes.ts` 提供 list/new/edit/agents/run；不需要路由迁移。离开时的脏表单保护沿用 `useWorkflowLeaveGuard`。
- `WorkflowWorkbench.tsx` 将模板、已有工作流、顶部导航都用同等视觉权重的卡片呈现；截图 `01-final-workbench-1024x700.png` 中只露出两条大卡片，工作流操作与历史被推到折叠区。
- `AgentManager.tsx` 的每位 Agent 有 4 个独立段落和操作行；截图 `02-final-agent-published.png` 在 700px 高度仅见一位半。小于 1100px 时编辑器整块掉到列表下面，容易误以为「编辑」没有反馈。
- `WorkflowEditor.tsx` 的保存与启动分处长表单底部，步骤卡片中依赖/高级项占据大量高度；截图 `12-final-created-workflow.png` 中一个步骤已超过半屏。`start` 会调用真实模型，脏表单时必须保持禁用；不可暗中自动运行。
- `WorkflowRunDetail.tsx` 的输入、用量、每个尝试、所有产物和原始事件同时铺开；截图 `13-final-created-run-completed.png` 的进度不直观，`06-parallel-review-two-artifacts.png` 与 `08-failed-then-retried-unknown-usage.png` 中 UUID、SHA、内部代码与重复用量挤占注意力。
- `workflows.css` 仅有少量通用样式，`workflow-card`/`workflow-columns` 等粗粒度复用造成所有内容都同级。现有 `WorkflowWorkbench.test.tsx` / `WorkflowShell.test.tsx` 覆盖核心创建、保存、运行、取消、恢复、导航，应继续通过并增加可见性/响应式断言。

## 目标信息架构和交互

1. **工作流库**：紧凑页眉（Team 工作台 + 简短说明）与二级导航「工作流 / Agent 成员」同一行，主要 CTA 独立。模板变成两条横向「快速开始」选项；我的工作流使用整齐的列表行，统一名称/说明/步骤/版本/操作列。空状态显示明确的创建入口，错误显示重试。
2. **Agent 成员**：左侧密集列表（名称、角色、状态、模型、工具权限一行/两行），右侧始终可见的编辑面板；选中态、创建个人副本、发布/归档操作语义清楚。宽度不足时纵向堆叠，但「编辑」会滚动并聚焦表单标题；保存后返回创建态并给出反馈。不要把后端状态当成英文内部字串裸露。
3. **工作流编辑器**：抬头表单、步骤链、保存区三段；每步显示编号 + Agent + 依赖摘要，编辑字段紧凑排列，高级项默认折叠。已保存版本有明确「启动运行」侧区（不足宽度时在步骤下方）与运行历史密集行，输入提示明确真实模型调用/Token 消耗。保存按钮/禁用态可在滚动中识别。
4. **执行详情**：顶部摘要显示运行名、状态、已完成/总步骤、实时连接状态和取消/恢复；主要区域是步骤时间线，默认只展开正在执行、失败或待重试的尝试，历史输出按需展开。原始目标、Token 用量、产物、事件作为次级披露区；错误提示与重试原因保留但不误报成功。所有原始 ID/SHA 移至「技术详情」，便于排障而非占据首屏。
5. **语义和状态**：中文英文完整翻译；明确运行中、等待依赖、等待重试、失败、取消中、已取消、已中断与断线重读。正确展示未知 Token 用量（绝不当 0）；错误码及原始消息仍可检查。按钮禁用与提示应解释保存/运行区别。

## 视觉系统与响应式

- 内容宽度自然铺满可用区，桌面主区左右留白 20–28px；统一 4/8/12/16/24px 间距，输入最小 40px、关键操作最小 44px，字阶 12/13/15/20/26px，信息层级遵循标题 > 操作 > 主内容 > 辅助元数据。
- 低层级数据使用分隔线与紧凑行，而非为每个数字套卡片。页面主体仅用少数清晰面板（例如编辑器/运行摘要），一套 8–10px 圆角，避免渐变和复杂阴影。标签和状态颜色由主题 token 驱动。
- 采用容器可用宽度而不是仅看窗口宽度：宽主区可以左右分栏；侧栏展开的 1024×700 与 800px 窄窗口依次收为单栏；不横向溢出，长名称和路径可折行；保持 44px 可点击区域及键盘焦点。
- 明暗色和中英文统一检查：长英文词/多字中文、100%/125% 缩放、深浅主题、1024×700、宽屏和窄窗。仅通过 DOM 不算验收。

## 风险和回滚

- 视觉压缩可能弱化首次使用提示：保留模板描述、运行费用提示和空状态；通过真实小白路径验证，而非只追求信息密度。
- 响应式的双栏可能让编辑按钮看似无效：宽屏选中项对应明确的右侧表单；窄屏点击滚动到表单。
- SSE 增量更新不得强制重置 `<details>` 展开状态，失败/重试/取消也不能被压缩成「完成」；不改 `useWorkflowRun` 的读回及投影语义。
- UI 回滚以独立前端提交为界；API 和持久化不变。提交后如回归，做修复提交，不使用破坏性 Git 命令。
