# 桌面 V2：不用写代码的多 Agent Team 编排

适用版本：2026-10-29 的 Team Workflow V2 文本 MVP。

## 先明确它能做什么

在一个工作流里安排多位 Agent：各自有名称、角色、系统提示词及模型选择，
按步骤交接资料，或分头分析后再汇总。你可以查看每一步的状态、结果、重试、
耗时和 Token，用取消按钮停止整次运行，重启后查看历史或显式恢复中断运行。

**本期是文本协作，不是自动操作电脑或自动联网的团队。**
规划者、研究员、编码者等是分工标签，不自动授予工具权限。研究员分析的是
你提供的材料；编码者可以生成代码文本，但不能读取工程、运行命令或提交 Git。
现有单 Agent、Computer Use、图片生成、桌面宠物和模型设置保持原有入口。

## 1. 第一次运行：从模板开始

1. 在现有「大模型设置」配置一个可用的主模型。已有配置不需要重新设置。
2. 点击桌面左侧 **Team 编排工作台**。
3. 在「从内置模板开始」选择：
   - **规划 → 调研 → 审查**：上一步完成后继续下一步。
   - **规划 → 并行调研 → 审查**：规划后两位研究员分别分析，审查者等待两份结果。
4. 模板会创建个人 Team 和已发布的个人 Agent。你可以直接使用，也可以修改名称、
   每一步的任务和依赖。
5. 点击 **保存工作流 / 保存新版本**。保存本身不会调用模型。
6. 在 **目标 / 输入** 填写任务目标、资料、约束和输出格式，点击 **启动真实运行**。
   **正式使用时会调用你配置的模型并消耗 Token，可能产生费用。**
7. 在运行详情查看步骤卡片、产物和事件时间线。刷新页面只回读已有运行，
   不会再提交一份任务。

可复制的输入：

```text
目标：比较下面两个内部培训方案，给出一页决策建议。
资料：方案 A 是两次各 1 小时的线上讲解；方案 B 是一次 2 小时的工作坊。
约束：10 位初学者，预算相同，不能假设已有更多调研数据。
输出：比较表、推荐方案、三项风险；明确哪些是事实、哪些是推测。
```

## 2. 创建自己的 Agent

进入 **Agent 成员 → 新建 Agent**：

- **名称**：例如「风险分析员」。
- **角色**：选择研究员/审查者等；角色不改变权限。
- **系统提示词**：描述分工、判断标准和输出格式，勿放 API Key 或其他秘密。
- **模型**：默认「继承主模型」；也可选择已有 Provider 和模型。这里不保存密钥，
  密钥仍由现有模型设置管理。命名 Provider 的固定模型与所选模型不符时会明确报错。
- **工具：无权限**：首期固定，不自动继承 Shell、文件、浏览器、MCP 或桌面操作。

先 **保存 Agent 草稿**，再点击对应卡片的 **发布**。工作流只能选择已发布、
无工具授权的文本 Agent。修改会形成新版本，已经保存或正在运行的 Team 不会
悄悄切换到新 Agent。共享、内置或文件来源的 Profile 可先创建个人副本再使用。

## 3. 自由配置工作流，而不是画复杂画布

点击 **新建工作流**，添加步骤并为每一步选择已发布的 Agent。

- **顺序执行**：自动连接前后步骤。
- **并行执行**：多个步骤没有相互依赖，可同时执行。
- **自定义依赖**：勾选「等待这些步骤完成」。例如：

```text
规划 → 方案分析 ─┐
     → 风险分析 ─┴→ 审查
```

审查步骤勾选「方案分析」和「风险分析」，就会等待两个步骤成功，并接收两份
产物。只会传递明确声明的直接依赖产物，不把所有 Agent 的聊天记录混在一起，
也不把其他 Agent 的系统提示词转交给下游。

循环、自我依赖、缺失 Agent、超限预算等会被拦截。保存新的工作流版本不改变
历史 Run；在最新 Team 页面「运行记录 · 全部版本」里可打开旧版 Run；旧版模板定义仍可通过版本 API 读取。

### 高级限制

- 最多 16 个步骤；工作流并行数 1–4。
- 默认单步 120 秒，最大 300 秒；默认整次 600 秒，最大 1800 秒。
- 每一步最多 3 次尝试，**包含第一次**，不是再额外重试 3 次。
- 默认总预算 32,000 Token，最大 128,000；实际可运行次数受上下文与保守预留影响。
- 每个用户最多排队 20 次，运行器还有全局并发和每用户运行限制。

模型内部的网络重试与节点级重试不同：网络请求暂时不可用时，客户端可能先重试；
最终失败后，由节点策略决定是否创建下一次 attempt。

## 4. 看懂运行状态

| 状态 | 含义 / 建议 |
| --- | --- |
| 排队中 / 待执行 | 等待运行容量或上游依赖，不表示模型已经收到请求 |
| 执行中 | 当前 Agent 正在请求模型；本期不展示隐藏思考链 |
| 等待重试 | 已记录失败，按有界策略稍后创建下一次 attempt |
| 已阻塞 | 必需的上游失败，当前步骤不会冒充执行成功 |
| 已完成 | 必需步骤成功，结果和事件已写入持久化 |
| 失败 / 已超时 | 打开步骤查看安全错误信息和尝试次数，不自动宣称成功 |
| 正在取消 / 已取消 | 已请求停止 / 已记录取消终态；不会把取消后迟到结果当产物 |
| 已中断 | 服务停止或执行权丢失；请检查已完成步骤再决定恢复 |

输出会先收集并清洗，再交给产物/事件展示；因此模型正在请求时未必有逐字文本。
结果中的 SHA-256 用于识别产物内容，不是模型真实性或联网证明。

**用量未知不等于零消耗。** 提供方没有返回完整 usage 时，页面标记「未知」，
并单独显示保守预留。预留不是实际 Token 也不是费用，不能据此推导价格。

## 5. 取消、重启与恢复

- 在运行详情点击 **取消运行**，等待状态变成「已取消」。
- 服务重启后，运行历史、attempt、事件、已完成产物仍在原 SQLite 中。
- 对「已中断」运行可点 **恢复中断运行**。系统用当前 revision 防止重复恢复，
  保留已完成节点，仅重新安排允许恢复的未完成步骤。
- 配置的模型/endpoint/fallback 路线变更、deadline 已过或预算不足时可能拒绝恢复；
  修正配置后新建运行，而不是篡改旧运行。密钥轮换不等同于模型路线变更。
- 强制终止服务后可能需要等待租约过期，才会变成可检查的中断状态。
- 本期**没有暂停/继续或人工审批节点**；恢复中断不等于在任意位置暂停/继续。

## 与 screen 启动的 Profile 是什么关系？

**整合而不是替代。** Agent 定义复用 Profile，工作流定义复用 Team，
但 V2 调度器在桌面本地服务里运行，不接管 screen/channel Worker 的进程、
会话或工具权限。旧 channel Team 不会误执行 V2 工作流，旧 Task 接口也不能
绕过编排器改写它拥有的任务。后续接入远程 Worker/Computer/Image executor
应通过独立执行器端口，不通过复制或放大现有 Profile 权限。

## 开发者离线验证

不需要任何真实密钥，使用 stdlib loopback fixture：

```sh
python3 scripts/test-workflow-offline-provider.py
python3 scripts/test-workflow-integration-gate.py
python3 scripts/run-workflow-integrated.py --binary /absolute/path/to/niuma
```

集成 runner 创建并清理独立配置/SQLite/工作目录，只访问 literal-loopback，
并显式拒绝业务数据库。浏览器截图不能代替真实 Wails 原生窗口验收。

部署紧急关闭执行可设置 `NIUMA_WORKFLOW_READ_ONLY=1` 后重启本地服务：
不启动调度器、不接受写命令，仍可读历史。MySQL 必须先显式执行 000029 迁移；
旧库/半迁移库保持旧服务可用，不自动启用 Workflow。
